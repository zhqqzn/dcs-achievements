# Achievement #2 - Линейная клиент-серверная архитектура

Необходимо спроектировать и описать на языке UML  классическую линейную 3-х уровневую архитектуру: 

[КЛИЕНТ]<->ВЕБ-СЕРВЕР<->СЕРВЕР ПРИЛОЖЕНИЙ<->БАЗА ДАННЫХ. 

Задача которую должна выполнять система:
1. Обрабатывать HTTP POST запрос в котором передается натуральное число от 0 до N, в ответ на запрос отправлять число увеличенное на единицу.
2. Обрабатывать исключительную ситуацию #1: если число уже поступало то выводить ошибку в ответ и лог.
3. Обрабатывать исключительную ситуацию #2: если поступившее число на единицу меньше уже обработанного числа то выводить ошибку в ответ и лог.

1. Стандартная сложность - разработать диаграмму компонентов для системы на языке UML (Component diagram).
2. Средняя сложность - выполнить задание стандартной сложности. Разработать диаграмму последовательностей для системы на языке UML (Sequence diagram).
3. Высокая сложность - выполнить задание средней сложности. Разработать систему на одном из языков программирования PYTHON/PHP/JS.


## Архитектура

```text
Клиент
  │ HTTP
  ▼
Nginx — веб-сервер / обратный прокси
  │ HTTP по внутренней сети Compose
  ▼
Сервер приложений: C++ / Drogon
  ├─ IncrementController — HTTP и JSON
  ├─ INumberService / NumberService — сценарий и правила
  └─ INumberRepository / PostgresNumberRepository — хранение и транзакции
       │ TCP/IP + SQL
       ▼
    PostgreSQL
```

Внешняя схема соответствует заданной цепочке: клиент → Nginx →
сервер приложений → PostgreSQL. Логически система разделена на
уровень представления и веб-доступа, прикладной уровень и уровень данных.

### Границы ответственности

- `IncrementController` проверяет HTTP-метод и синтаксис тела, а затем преобразует `ProcessResult` в HTTP-код и JSON. Он не содержит SQL и не решает бизнес-исключения.
- `INumberService` — интерфейс сценария обработки. `NumberService` реализует допустимый диапазон, порядок проверок, бизнес-результаты и журналирование. Он не зависит от Drogon, HTTP или конкретной СУБД.
- `INumberRepository` и `INumberTransaction` задают контракт транзакционных операций, нужных сценарию. В них нет SQL-типов Drogon или PostgreSQL.
- `PostgresNumberRepository` — инфраструктурный адаптер. Только здесь находятся SQL, параметры PostgreSQL и детали жизненного цикла транзакции Drogon.
- `stdout_logger` сериализует записи журнала, чтобы строки от асинхронных обработчиков не перемешивались.

Это схема «порты и адаптеры» в небольшом масштабе. Интерфейсы добавлены на границах, где действительно нужна замена реализации или независимое тестирование; каждый вспомогательный класс интерфейсом не обёрнут.

## Правила обработки

- Принимается только HTTP POST на `/api/increment`.
- Тело — одно десятичное неотрицательное целое число в ASCII. Знаки, пробелы, дроби и дополнительные поля не допускаются; ведущие нули разрешены.
- По умолчанию диапазон входного числа: от `0` до `9223372036854775806` включительно. Верхняя граница оставляет место для `n + 1` в знаковом `BIGINT`.
- **Исключение № 1:** число ранее поступало как корректный вход. Ответ — HTTP 409, `DUPLICATE_NUMBER`.
- **Исключение № 2:** число ещё не поступало, но `n + 1` ранее успешно обработано. Ответ — HTTP 409, `PREDECESSOR_OF_PROCESSED_NUMBER`.
- При отсутствии исключений число сохраняется как успешно обработанное, ответ содержит `n + 1`.
- Корректный вход регистрируется в `request_history` до проверки исключения № 2. Поэтому повторно отправленное число, ранее отклонённое по исключению № 2, вызывает исключение № 1.
- Другой HTTP-метод возвращает 405; некорректный формат — 400 `INVALID_NUMBER`; превышение `MAX_INPUT` — 400 `NUMBER_OUT_OF_RANGE`; ошибка хранилища — 503 `SERVICE_UNAVAILABLE`.
- Прикладные события и ошибки пишутся в `stdout`. Docker отображает stdout/stderr контейнеров через `docker compose logs`.

## Транзакции и конкурентные запросы

Каждый допустимый запрос выполняется в одной транзакции. Адаптер PostgreSQL блокирует единственную строку `request_state` на время операции. Благодаря этому два экземпляра приложения, подключённые к одному основному узлу БД, не могут одновременно пройти проверку истории и записать один и тот же новый вход. `NumberService` получает результат коммита до возврата итогового бизнес-ответа клиенту.

Эта схема намеренно сериализует все такие операции, что упрощает проверку корректности, но ограничивает пропускную способность при большом числе записей. Для практической работы по оптимизации можно сравнить её с блокировками по ключам или другими схемами транзакционной изоляции, сохраняя те же инварианты.

## Запуск

Требуются Docker Engine и Docker Compose v2. Если текущий пользователь
не имеет прав доступа к Docker Engine, перед командами `docker compose`
потребуется `sudo`.

```bash
cp .env.example .env
sudo docker compose up --build -d
```

Сервисы:

- Nginx: `http://localhost:8080`;
- приложение внутри сети Compose: `app:8080`;
- PostgreSQL внутри сети Compose: `database:5432`.

Проверить состояние:

```bash
docker compose ps
curl -i http://127.0.0.1:8080/healthz
```

Посмотреть журналы:

```bash
docker compose logs --tail=100 app
```

`MAX_INPUT`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` и `DB_PASSWORD` настраиваются через `.env`. Значения в `.env.example` рассчитаны только на локальную демонстрацию; перед доступом к сервису из внешней сети необходимо заменить пароль и настроить сетевую защиту.

Скрипт `database/001-schema.sql` выполняется официальным образом PostgreSQL только при первом создании пустого тома. Не выполняйте `docker compose down -v` на окружении с нужными данными: удаление тома безвозвратно удаляет состояние и историю запросов.

## Проверка

### Модульные тесты бизнес-логики

Модульные тесты используют тестовую реализацию `INumberRepository` в памяти и проверяют правила приложения без запуска PostgreSQL. Dockerfile запускает CTest после компиляции приложения:

- успех и повтор числа;
- исключение № 2 и превращение следующего повтора в исключение № 1;
- проверку верхней границы;
- обработку отсутствующей строки состояния.

Модульные тесты можно собрать отдельно от веб-фреймворка и СУБД — нужны только CMake и C++17-компилятор:

```bash
cmake -S . -B build-unit -DBUILD_HTTP_SERVER=OFF -DBUILD_TESTING=ON
cmake --build build-unit --parallel 2
ctest --test-dir build-unit --output-on-failure
```

Для сборки полного приложения дополнительно требуется установленный Drogon:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_HTTP_SERVER=ON -DBUILD_TESTING=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
```

Docker-сборка устанавливает Drogon, затем выполняет эти же модульные тесты в build-стадии до создания runtime-образа.

### Интеграционные тесты API

Тесты `tests/test_api.py` написаны на Python с использованием
стандартного модуля `unittest`. Они обращаются к работающей системе
через HTTP и проверяют:

- успешную обработку запроса и обе бизнес-ошибки;
- пустое тело, текст, дробные и отрицательные числа;
- знак `+`, пробелы вокруг числа и переполнение целого типа;
- выход за допустимый диапазон;
- запрет других HTTP-методов;
- конкурентные запросы с одинаковым числом.

Для запуска тестов необходимо предварительно запустить систему:

```bash
sudo docker compose up --build -d
python3 -m unittest discover -s tests -v
```

## Демонстрация

```bash
URL=http://127.0.0.1:8080/api/increment

curl -i -X POST "$URL" --data-binary '700000000000'
curl -i -X POST "$URL" --data-binary '700000000000'
curl -i -X POST "$URL" --data-binary '699999999999'
sudo docker compose logs --since=2m app
```

Первый запрос возвращает `200` и `700000000001`, второй — `DUPLICATE_NUMBER`, третий — `PREDECESSOR_OF_PROCESSED_NUMBER`, если эти числа ещё не использовались.
